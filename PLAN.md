# tg-proxy-2 — панель и Telegram-бот для Telegram WEB proxy (tproxy-server)

План для Claude Code. Репозиторий: `https://github.com/barakov-dot/tg-proxy-2.git`
Апстрим прокси: `https://github.com/telegramdesktop/tproxy-server` (proof-of-concept, активно меняется).

Разработка ведётся на macOS, **локально ничего не запускается, кроме unit-тестов**. Всё готовится под деплой на удалённый сервер (Ubuntu 24.04 или Debian 13, x86_64, от root) через инсталлятор из GitHub.

## 1. Цель

Над уже установленным tproxy-server добавить:

- веб-панель на отдельном поддомене, по случайному пути, с логином и паролем;
- Telegram-бота (пользовательская и админская части);
- по одному профилю (своя ссылка/секрет) на пользователя, с учётом трафика, сроками действия, включением/выключением, удалением, рассылкой ссылок;
- бэкап перед каждой манипуляцией и автоматический откат при сбое;
- установку одной командой из GitHub.

Принятые решения (подтверждены владельцем):

| Вопрос | Решение |
|---|---|
| Учёт трафика по пользователям | свой loopback-адрес `127.64.x.y` на профиль + счётчики nftables; прокси не патчим |
| Стек | Python 3.12+, FastAPI, aiogram 3, SQLite, серверные шаблоны + HTMX |
| Масштаб | 50–300 пользователей онлайн |
| Уже существующие профили прокси (включая `default`) | импортируются как пользователи панели с комментарием `import`, ссылки продолжают работать (раздел 3.10) |
| Когда применять изменения | сразу после каждой операции, без отложенной очереди (раздел 3.6) |
| Лимит устройств/сессий на пользователя | не делаем |

## 2. Факты об апстриме (прочитано в README, PLAN.md, PUBLIC_SITE.md, deploy/*, internal/*)

### 2.1 Схема

```
Internet :80/:443 -> Caddy -> 127.0.0.1:8080 tproxy-server (relay) -> публичный сайт
                                              \-> 127.0.0.1:2398 официальный MTProxy
```

- Наружу слушает только Caddy. Relay: `127.0.0.1:8080` (публичный), `127.0.0.1:8081` (админ: `/healthz`, `/readyz`, `/metrics`).
- На hostname прокси Caddy обязан отправлять **все** пути в relay. Панель туда вешать нельзя → отдельный поддомен.
- В `Caddyfile` апстрима стоит `admin off` → `caddy reload` невозможен, только `systemctl restart caddy`.
- Caddy — бинарник `/usr/local/bin/caddy`, unit `/etc/systemd/system/caddy.service`, переменные `TPROXY_HOSTNAME`, `TPROXY_SITE_ROOT`, `ACME_EMAIL` в drop-in `/etc/systemd/system/caddy.service.d/tproxy.conf`. Для `caddy validate` эти переменные нужно передать в окружение.

### 2.2 Файлы и юниты, которые создаёт установщик прокси

| Путь | Что это |
|---|---|
| `/usr/local/bin/tproxy-server` | relay |
| `/etc/tproxy-server/config.json` | конфиг relay, `root:tproxy 0640` |
| `/etc/tproxy-server/profiles.json` | профили, `root:tproxy 0400`, в сервис попадает через `LoadCredential` |
| `/etc/tproxy-server/firewall.nft` | таблица `inet tproxy_backend`: drop не-lo на 2398, 8888 |
| `/opt/MTProxy/objs/bin/mtproto-proxy` | официальный MTProxy |
| `/etc/mtproxy/mtproxy.env` | `MTPROXY_SECRET`, `MTPROXY_WORKERS`, `MTPROXY_MAX_CONNECTIONS` (`root:mtproxy 0640`) |
| `/etc/mtproxy/proxy-secret`, `/etc/mtproxy/proxy-multi.conf` | данные Telegram, обновляются таймером |
| `/etc/caddy/Caddyfile` | активный конфиг Caddy |
| `/srv/tproxy-site` | публичный сайт |
| юниты | `tproxy-server`, `mtproxy`, `tproxy-firewall`, `caddy`, `refresh-mtproxy-config.{service,timer}` |

Строка запуска штатного MTProxy:
`mtproto-proxy -u mtproxy -p 8888 -H 2398 -S ${MTPROXY_SECRET} $MTPROXY_NAT_ARGS --aes-pwd /etc/mtproxy/proxy-secret /etc/mtproxy/proxy-multi.conf -M ${MTPROXY_WORKERS} -C ${MTPROXY_MAX_CONNECTIONS}`
`-H` — это порт, адреса привязки нет: MTProxy слушает `0.0.0.0`. `MTPROXY_NAT_ARGS` на NAT-хостах задаётся установщиком (в env-файле или drop-in) — его надо **унаследовать**.

### 2.3 Профили

```json
{"profiles":[{"name":"alpha","secret":"<32 hex>","backend":"127.0.0.1:2398","carrier_mode":"https",
  "limits":{"max_sessions":32, "...":"..."}}]}
```

- `name`: 1–64 символа, уникален. `secret`: 32 hex (или `dd`+32 hex, или base64url). `backend`: **любой числовой loopback-адрес** + порт (проверка `ip.IsLoopback()`, то есть весь `127.0.0.0/8`).
- `carrier_mode`: `https` (по умолчанию), `https-lanes`, `websocket`, `websocket-lanes`.
- Файл парсится с `DisallowUnknownFields` — лишние ключи = отказ старта.
- Профилей должно быть **от 1 до `limits.max_profiles`** (по умолчанию 32). Пустой список = relay не стартует.
- Права: никаких битов group/other (кроме чтения через systemd credential).
- Перечитывания на лету нет (обрабатываются только SIGINT/SIGTERM). **Любое изменение профилей = `systemctl restart tproxy-server`**, это рвёт сессии всех клиентов; клиенты переподключаются сами.
- Проверка без запуска: `tproxy-server -config <config> -profiles-file <profiles> -check`.

### 2.4 Лимиты

- **16 секретов** — предел официального MTProxy на один процесс (повторяющиеся `-S`). Это ограничение MTProxy, не relay.
- `max_profiles` relay — отдельный лимит, задаётся в `config.json`.
- Значения по умолчанию в `config.json`: `max_sessions_global` 128, `max_streams_global` 4096, `new_sessions_burst` 128, `max_bootstraps_global` 512, `new_bootstraps_burst` 256, `max_pending_global` 512 MiB. Лимиты профиля могут только понижать глобальные; пропущенное значение наследует глобальное.
- Relay отказывается стартовать, если резерв управляющих кадров × `max_sessions_global` не оставляет места в `max_pending_global` → любые изменения лимитов проверять через `-check`.

### 2.5 Метрики

`/metrics` отдаёт только **общие** счётчики: `tproxy_sessions_live`, `tproxy_streams_live`, `tproxy_bytes_up_total`, `tproxy_bytes_down_total`, `tproxy_sessions_created_total`, `tproxy_limit_hits_total` и т.п. Разбивки по профилям нет, в логах нет ни имён профилей, ни времени сессий. PLAN.md апстрима прямо говорит: если один MTProxy принимает несколько секретов, relay не может вести учёт по каждому.
`/readyz` при каждом вызове делает TCP-dial на backend **каждого** профиля.

### 2.6 Ссылка для клиента

`https://t.me/webproxy?server=<hostname>&secret=<secret>`; клиенты могут принимать и `tg://webproxy?server=...&secret=...`. README: публичный t.me этот маршрут пока не обслуживает — ссылку может понадобиться открывать прямо в клиенте.

### 2.7 Фактическое состояние сервера владельца (со слов владельца, секреты не настоящие)

Сервер уже изменён прежним ботом и **отличается от чистой установки апстрима**:

- `/etc/tproxy-server/profiles.json` — 15 профилей вида:
  ```json
  {"name": "user_93455874", "secret": "<32 hex>", "backend": "127.0.0.1:2398", "carrier_mode": "https"}
  ```
  Имя = `user_<Telegram ID>`. Все указывают на один backend `127.0.0.1:2398`. Блока `limits` нет.
- `/etc/mtproxy/mtproxy.secrets` — файл, которого нет в апстриме: по одному секрету (32 hex) в строке. Значит, `mtproxy.service` или его обвязка переделаны прежним ботом, чтобы собирать `-S` из этого файла. **Ничего не предполагать о его ExecStart** — читать фактический юнит и drop-in.
- Все 15 секретов живут в одном процессе MTProxy; при попытке добавить ещё процесс перестаёт работать (у владельца упёрлось на 15, по документации предел 16 — см. 3.2).
- Прежний бот владелец остановит сам при установке панели.

Фикстуры в `tests/fixtures/upstream/` делать в двух вариантах: чистый апстрим и этот (с `user_<id>` и `mtproxy.secrets`).

### 2.8 Важное предупреждение

Апстрим — PoC и быстро меняется: в `master` код уже использует поля конфига, которых нет в документации (`BasePath`, `TokenKeyFile`, `StaticRoutes`). Следствия:

- `config.json` **никогда не генерировать с нуля** — читать как JSON, менять только нужные ключи в `limits`, остальное сохранять байт-в-смысл;
- ExecStart для пула MTProxy строить на основе реально установленного `/etc/systemd/system/mtproxy.service`, а не хардкодить;
- инсталлятор фиксирует версию установленного relay (sha256 бинарника) и предупреждает, если она не из списка проверенных.

## 3. Архитектура решения

### 3.1 Пользователь = профиль + секрет + loopback-адрес

- Каждому пользователю при создании генерируется секрет (`secrets.token_hex(16)`), имя профиля `u<id>` (никаких персональных данных в конфиге прокси), и выделяется адрес из `127.64.0.0/16`: `127.64.<hi>.<lo>`, пропуская `.0` и `.255`.
- Профиль в `profiles.json`: `backend = "127.64.x.y:<порт пула>"`.
- MTProxy слушает `0.0.0.0:<порт>`, поэтому принимает соединение на любой адрес `127/8` **[ПРОВЕРИТЬ НА СЕРВЕРЕ]**. У relay в юните `IPAddressAllow=localhost` — это весь `127.0.0.0/8`.
- Так несколько пользователей делят один процесс MTProxy (до 16 секретов), но трафик каждого виден по адресу назначения.

### 3.2 Пул процессов MTProxy (правило 16 секретов)

- Шаблонный юнит `tgpanel-mtproxy@.service` — собственный, не копия ExecStart установленного `mtproxy.service` (тот переделан прежним ботом, см. 2.7). Из установленного юнита и его drop-in берутся только: путь к бинарнику, пользователь, `--aes-pwd`, путь к `proxy-multi.conf`, NAT-аргументы. Hardening-настройки — из апстримного `deploy/mtproxy.service`. `EnvironmentFile=/etc/tgpanel/mtproxy/%i.env`:
  `MTP_PORT`, `MTP_STATS_PORT`, `MTP_SECRET_ARGS="-S aaa -S bbb ..."` (подстановка без кавычек), `MTP_WORKERS=1`, `MTP_MAX_CONNECTIONS=4096`, `MTP_NAT_ARGS` (унаследован).
- Диапазоны портов (резерв на 64 процесса = 1024 пользователя): клиентские `2400–2463`, статистика `8900–8963`.
- Настройка `secrets_per_process`, по умолчанию **16** (предел MTProxy), допустимо 1–16. У владельца процесс переставал работать уже после 15 секретов, поэтому инсталлятор проверяет предел практикой (фаза 8, п. 4), а при сомнении значение снижается до 15 одной настройкой — без переделки кода. Аллокатор: новый пользователь попадает в первый пул, где секретов < 16; если таких нет — создаётся новый пул (env-файл, `systemctl enable --now`). Пул без секретов останавливается и отключается.
- Секрет **выключенного** пользователя остаётся в MTProxy (слот занят) — блокировка делается удалением профиля из relay, так включение/выключение не требует рестарта MTProxy.
- Секрет **удалённого** пользователя убирается из env пула → рестарт только этого пула (задевает максимум 16 пользователей).
- Старый процесс `mtproxy.service` (порт 2398) после импорта не обслуживает ни одного профиля. Его файлы (`mtproxy.env`, `mtproxy.secrets`, юнит) не изменяем и не удаляем — они нужны для отката и `uninstall`. По умолчанию он остаётся запущенным вхолостую: в `tproxy-server.service` стоит `Wants=mtproxy.service`, поэтому простое `stop`/`disable` не держится — systemd поднимет его при следующем рестарте relay (а рестарты у нас частые). Если владелец хочет его убрать — `tgpanel legacy-mtproxy off` делает `systemctl mask --now mtproxy.service` (и `on` — обратно); предлагать это только после успешной проверки импорта.
- `refresh-mtproxy-config` апстрима рестартует только штатный `mtproxy`. Добавить свой `tgpanel-mtproxy-refresh.path` (следит за `/etc/mtproxy/proxy-multi.conf`) → рестарт всех пулов по очереди.

### 3.3 Сторожевой профиль

Relay не стартует с пустым списком профилей. Поэтому, **только когда активных профилей нет** (все выключены/удалены), в `profiles.json` пишется один профиль `_tgpanel_sentinel` со случайным секретом, который нигде не показывается и никому не выдаётся. Его backend — порт первого нашего пула (не 2398: от старого процесса не зависим), пул при этом остаётся запущенным с этим же секретом. Как только появляется активный пользователь, сторожевой профиль убирается.

### 3.4 Учёт трафика: nftables

Собственная таблица (чужую `inet tproxy_backend` не трогаем):

```
table inet tgpanel {
  set up   { type ipv4_addr; counter; }   # relay -> MTProxy, по адресу назначения
  set down { type ipv4_addr; counter; }   # MTProxy -> relay, по адресу источника
  chain acct {
    type filter hook output priority 0; policy accept;
    oifname "lo" meta l4proto tcp ip daddr @up
    oifname "lo" meta l4proto tcp ip saddr @down
  }
  chain guard {
    type filter hook input priority -10; policy accept;
    iifname != "lo" tcp dport { 2400-2463, 8900-8963 } drop
  }
}
```

- Считаем только в `output`, чтобы не удвоить пакеты loopback.
- Элементы наборов добавляются/удаляются на лету (`nft add element` / `delete element`), без перезагрузки правил. Полный файл `/etc/tgpanel/tgpanel.nft` перегенерируется при каждом apply; сервис `tgpanel-firewall.service` привязан к `nftables.service` так же, как `tproxy-firewall` у апстрима (иначе `flush ruleset` дистрибутива снесёт таблицу и откроет порты пула).
- Счётчики на элементах набора требуют nftables ≥ 0.9.5 и ядро ≥ 5.7 — на Ubuntu 24.04 и Debian 13 есть **[ПРОВЕРИТЬ НА СЕРВЕРЕ]**. Инсталлятор проверяет это пробным созданием набора; если не работает — fallback на именованные счётчики (`counter u123_up {}` + правило на пользователя).
- Байты считаются с заголовками IP/TCP — в панели подписать «трафик (с накладными расходами)».

### 3.5 Коллектор

- Каждые 30 с (настройка) читает `nft -j list set inet tgpanel up|down`, считает дельты, пишет в SQLite.
- Сброс счётчика (дельта < 0: перезагрузка, reload правил) → новое значение считается базой, отрицательная дельта не пишется.
- Хранение: минутные бакеты 14 дней → часовые 180 дней → суточные бессрочно (сроки — настройки). Ночной rollup.
- **Первое соединение / последняя активность**: фиксируются, когда дельта за опрос превышает порог (по умолчанию > 2 КБ и > 10 пакетов). Порог нужен, потому что `/readyz` и проверки после apply делают пустые TCP-подключения на адрес каждого профиля. Точность времени = интервал опроса. В интерфейсе честно называть «первое соединение» и «последняя активность».
- «Онлайн» = активность в двух последних опросах.
- Панель в штатном режиме опрашивает только `/healthz` и `/metrics`; `/readyz` — только один раз после apply.

### 3.6 Конвейер применения изменений (apply) — ядро проекта

Источник истины — SQLite. Файлы прокси — производные. Один глобальный `flock`, шаги:

1. **Бэкап** → `/var/backups/tgpanel/<UTC-время>-<причина>.tar.gz` (`0600`): `/etc/tproxy-server/{config.json,profiles.json}`, `/etc/mtproxy/mtproxy.env`, `/etc/tgpanel/**`, `/etc/caddy/Caddyfile`, снимок SQLite (через backup API, не копированием файла). Хранить последние 50 + по одному за день на 30 дней (настройка).
2. **Рендер** желаемого состояния во временные файлы: `profiles.json`, изменённый `config.json` (только `limits`), env-файлы пулов, `tgpanel.nft`.
3. **Проверка**: `tproxy-server -config <tmp> -profiles-file <tmp> -check`; свои инварианты (≤ `secrets_per_process` секретов на пул, уникальность адресов/секретов/имён, профилей ≥ 1 и ≤ `max_profiles`).
4. **Атомарная замена** (`rename` в том же каталоге) с исходными владельцем и правами.
5. **Рестарты** только того, что изменилось: затронутые пулы MTProxy (ждать открытия порта) → элементы nft → `tproxy-server` → ждать `/healthz`, затем `/readyz` (до 20 с).
6. **Сбой на любом шаге** → восстановление файлов из бэкапа шага 1, рестарт сервисов, запись в `apply_runs`, уведомление админам в бот, красный баннер в панели. Изменение в БД откатывается вместе с файлами: операция считается невыполненной, её можно повторить.

**Применение — немедленное.** Отложенной очереди и кнопки «Применить» нет: каждая операция (создать, удалить, включить, выключить, продлить, перевыпустить секрет) сама запускает apply и завершается только после того, как relay перезапущен и `/readyz` отвечает. Рестарт быстрый, это допустимо. Следствия:

- ссылка показывается в панели и отправляется в бот **только после успешного apply** — пользователь получает уже рабочий прокси;
- одна операция = один apply, даже если она затрагивает много пользователей (пакетное создание 20 штук, массовое удаление по чекбоксам, импорт, все истёкшие за одну минуту) — один рестарт на операцию, а не на пользователя;
- операции выполняются строго по очереди (глобальная блокировка); если apply уже идёт, следующая операция ждёт, а пришедшие за время ожидания изменения применяются одним следующим apply;
- в панели и боте на время операции показывать «применяется…», затем результат; при сбое — откат и сообщение об ошибке, операция считается невыполненной.

Что требует какого рестарта:

| Операция | Пул MTProxy | Relay |
|---|---|---|
| создать пользователя | рестарт одного пула | рестарт |
| выключить / включить / срок истёк / продлили | — | рестарт |
| удалить | рестарт одного пула | рестарт |
| перевыпустить секрет | рестарт одного пула | рестарт |
| изменить carrier_mode | — | рестарт |
| изменить имя / комментарий / Telegram ID | — | — (только БД) |

### 3.7 Автонастройка лимитов relay (масштаб 50–300)

При apply пересчитывать и записывать в `config.json` → `limits` (остальные ключи файла не трогать):

- `max_profiles` = max(32, число профилей + 16);
- `max_sessions_global` — настройка, по умолчанию 1024;
- `new_sessions_burst` ≥ `max_sessions_global`, `new_bootstraps_burst` и `max_bootstraps_global` ≥ `max_sessions_global` — иначе после каждого рестарта relay одновременное переподключение всех клиентов упрётся в burst 128;
- `max_streams_global` — по умолчанию 16384; сумма `-C` пулов должна её покрывать;
- лимитов на профиль **не задаём**: блок `limits` в профилях не пишется, каждый профиль наследует глобальные значения. Ограничение пользователя — только включить/выключить.

Если `-check` отклоняет бюджет (`max_pending_global`) — не применять, показать в панели, что упёрлись в память, и предложить значение.

### 3.8 Панель в Caddy

В `/etc/caddy/Caddyfile` добавляется блок между маркерами `# >>> tgpanel` / `# <<< tgpanel` (блок прокси не меняется):

```
panel.example.com {
	encode zstd gzip
	header Strict-Transport-Security "max-age=31536000"
	@panel path /<RANDOM>/*
	handle @panel {
		reverse_proxy 127.0.0.1:8090
	}
	handle {
		respond 404
	}
}
```

- `<RANDOM>` — ≥ 22 url-safe символа, генерирует инсталлятор. Приложение работает с `root_path=/<RANDOM>`.
- Перед заменой: бэкап, `caddy validate` (с переменными из drop-in), затем `systemctl restart caddy` (разрыв на секунды, один раз при установке).
- Access-логи не включать ни для одного сайта.

**Сертификат для домена панели (Let's Encrypt).** Отдельный выпуск (certbot и т.п.) не нужен и запрещён: сертификаты ведёт сам Caddy, который уже стоит на сервере.

- Достаточно добавить блок сайта с доменом панели: Caddy при старте сам получает сертификат у Let's Encrypt (запасной центр — ZeroSSL) по ACME, используя почту из глобального блока (`email {$ACME_EMAIL}`, уже задана установщиком прокси), и сам его продлевает.
- **Если сертификат на этот домен уже есть** в хранилище Caddy (повторная установка, обновление, `repair`) и он действителен — Caddy использует его, нового выпуска не происходит. Это штатное поведение, свою логику поверх не писать и файлы сертификатов вручную не трогать. Хранилище Caddy (`/var/lib/caddy`) при обновлении и `uninstall` не удалять — иначе повторные выпуски упрутся в лимиты Let's Encrypt.
- **До** изменения Caddyfile инсталлятор проверяет условия выпуска: A-запись домена панели указывает на публичный IPv4 этого сервера; AAAA-записи либо нет, либо она тоже ведёт на этот сервер (битая AAAA ломает проверку); порты 80 и 443 слушает Caddy. При несовпадении — понятное сообщение, что исправить в DNS, и вопрос «продолжить / прервать» (по умолчанию прервать).
- **После** рестарта Caddy инсталлятор ждёт сертификат до 120 с: запрос `https://<домен панели>/` с проверкой цепочки и имени. Затем печатает издателя и срок действия; отдельно отмечает, был ли сертификат выпущен сейчас или взят существующий (по дате начала действия).
- Если за 120 с сертификата нет: показать последние строки `journalctl -u caddy` с причиной (DNS, недоступен порт 80, лимит запросов), сказать, что Caddy продолжит попытки сам, и что панель заработает без переустановки, как только причина устранена. Прокси при этом не затронут — его блок и сертификат не менялись.
- `tgpanel doctor` и дашборд показывают срок действия сертификата панели и предупреждают, если осталось меньше 14 дней (значит, автопродление не работает).
- В тестах на `FakeSystemOps`: сертификат уже есть; выпущен новый; не получен за время ожидания.

- Повторный запуск установщика прокси перезаписывает Caddyfile → команда `tgpanel repair` возвращает блок.
- Случайный путь — только сокрытие; защита — логин/пароль (раздел 5.1).

### 3.9 Процессы

Один сервис `tgpanel.service` (root): в одном asyncio-процессе uvicorn (127.0.0.1:8090) + aiogram long polling + планировщик + коллектор. Один процесс = один владелец SQLite и apply-блокировки. Вебхук для бота не нужен.

### 3.10 Импорт существующих профилей

На сервере уже есть рабочие профили, выданные другим ботом. Их надо забрать в панель так, чтобы **ссылки у людей не поменялись**.

Источник — текущий `/etc/tproxy-server/profiles.json`. Для каждого профиля (кроме нашего `_tgpanel_sentinel`):

- секрет сохраняется как есть (вместе с префиксом `dd`, если он был: от точного значения зависит ссылка); в MTProxy передаётся базовый секрет без `dd`;
- секрет добавляется в наш пул по правилу 16 на процесс, `backend` профиля переписывается на `127.64.x.y:<порт пула>` — так импортированные сразу попадают в учёт трафика;
- профиль в `profiles.json` переименовывается в `u<id>` (имя клиенту не видно), исходное имя сохраняется в БД в `source_profile_name`;
- `carrier_mode` профиля сохраняется; блок `limits`, если был, отбрасывается (лимитов на пользователя нет);
- поле «комментарий» = `import`; статус `active`; срок действия не задан (бессрочно, пока владелец не поставит срок) — чтобы импорт никого внезапно не отключил;
- `first_seen_at` / `last_seen_at` пустые: истории до импорта нет.

**Telegram ID.** У владельца имя профиля = `user_<Telegram ID>` (раздел 2.7). Правило по умолчанию: `^user_(\d{5,15})$` → `tg_id`; имя пользователя в панели = исходное имя профиля (владелец переименует при желании). Выражение настраивается на экране импорта; профиль, не подошедший под шаблон, импортируется без ID (вписать можно позже в карточке). Загрузка CSV `имя_профиля;telegram_id;имя;комментарий` остаётся как дополнительный способ.

**Сверка с MTProxy.** Перед импортом сравнить множество секретов из `profiles.json` с `/etc/mtproxy/mtproxy.secrets` (если файл есть) и с `MTPROXY_SECRET` из `mtproxy.env`:
- секрет есть в профилях, но не в MTProxy → предупреждение «профиль, вероятно, и сейчас не работает», импортировать всё равно;
- секрет есть в MTProxy, но не в профилях → показать как «неиспользуемый», не импортировать;
- дубли секретов или ID → блокирующая ошибка по этим строкам.

**Раскладка.** Для сервера владельца: 15 импортированных секретов → все в наш пул №1 (15 из `secrets_per_process`), следующий новый пользователь занимает оставшийся слот или открывает пул №2 — в зависимости от настройки предела. Старый процесс на 2398 остаётся без профилей (раздел 3.2).

**Порядок переключения (без простоя дольше одного рестарта):** поднять пул №1 со всеми секретами и дождаться открытия порта → записать `profiles.json` с новыми backend → рестарт relay → `/readyz`. Старый процесс до этого момента продолжает обслуживать всех; при сбое откат возвращает прежний `profiles.json`, и всё работает как до импорта.

**Экран предпросмотра** (панель → «Импорт», и `tgpanel import --dry-run` в CLI): таблица «исходное имя → Telegram ID → имя → пул → адрес», предупреждения (дубли ID, уже импортированные секреты, нераспознанные ID), правка значений до подтверждения. Подтверждение = одна операция = один apply с бэкапом и откатом.

Импорт идемпотентен: профиль с уже известным секретом пропускается. Инсталлятор при первой установке предлагает импорт сразу; позже он доступен из панели и CLI.

**Важно:** прежний бот после импорта должен быть остановлен — иначе он перезапишет `profiles.json` своей версией. Инсталлятор и экран импорта выводят это предупреждение, а `tgpanel doctor` и каждый apply сверяют хеш `profiles.json` с последним записанным нами и сообщают о постороннем изменении (не затирая его молча: показать разницу и предложить импортировать новые профили).

Пользователи, импортированные с Telegram ID, боту нового проекта ещё не писали: рассылка им невозможна, пока они не нажмут `/start` (раздел 6.3). При `/start` бот находит их по ID и сразу показывает их действующую ссылку.

## 4. Модель данных (SQLite, WAL)

- `users`: id, name, comment (свободный текст, редактируется; у импортированных = `import`), tg_id (nullable, unique), tg_username, secret, status (`active`/`disabled`/`expired`), disabled_reason, pool_id, loopback_ip (unique), carrier_mode (nullable = глобальная), created_at, expires_at (nullable), first_seen_at, last_seen_at, can_message (bool), bot_started (bool), imported (bool), source_profile_name (nullable)
- `pools`: id, port, stats_port, managed (bool), created_at
- `traffic_minute` / `traffic_hour` / `traffic_day`: user_id, bucket_ts, bytes_up, bytes_down, packets_up, packets_down
- `counter_state`: user_id, last_up, last_down, last_packets_up, last_packets_down
- `access_requests`: id, tg_id, tg_username, full_name, status (`pending`/`approved`/`rejected`), created_at, decided_by, decided_at
- `settings`: key, value
- `admins`: tg_id, added_at
- `apply_runs`: id, started_at, finished_at, status, reason, backup_path, error
- `backups`: id, path, created_at, reason, size
- `broadcasts` + `broadcast_items`: кто, когда, шаблон, получатель, результат
- `audit_log`: ts, actor (`web:<login>` / `bot:<tg_id>` / `system`), action, target, details

Все времена в UTC; отображение — в часовом поясе из настроек.

## 5. Веб-панель

### 5.1 Вход и безопасность

- Логин + пароль (argon2id). Сессия в cookie: `HttpOnly`, `Secure`, `SameSite=Strict`, `Path=/<RANDOM>/`, время жизни 12 ч.
- CSRF-токен на все изменяющие запросы; ограничение попыток входа (5 в минуту на IP, затем пауза с нарастанием); строгий CSP, статика только своя (никаких CDN).
- Секреты и ссылки в интерфейсе скрыты по умолчанию, показ по клику. В логи секреты не пишутся никогда.

### 5.2 Страницы

1. **Дашборд**: всего / активных / онлайн; суммарный трафик за 24 ч и 30 дней; ёмкость (пулы и занятые слоты, `tproxy_sessions_live` против `max_sessions_global`, `tproxy_limit_hits_total`); здоровье сервисов; индикатор идущего apply и баннер последнего сбоя.
2. **Пользователи** — общий список:
   - колонки: ID, имя, комментарий, Telegram ID, username, статус, онлайн, создан, срок действия, первое соединение, последняя активность, трафик за выбранный период (вверх / вниз / всего; период списка: 24 ч / 7 дней / 30 дней / всё время), пул, «бот запущен»;
   - **сортировка по любой колонке**, по возрастанию и убыванию (клик по заголовку); выполняется на сервере, чтобы работала на всём списке, а не на текущей странице;
   - **фильтры**: быстрый поиск по имени / комментарию / Telegram ID / username; статус (активен / выключен / истёк); онлайн; импортированные; «с Telegram ID / без»; «бот запущен / нет»; срок истекает в ближайшие N дней; диапазоны дат для «создан» и «последняя активность»; трафик больше/меньше значения; текстовый фильтр по комментарию (например `import`);
   - фильтры и сортировка хранятся в параметрах URL (ссылку на выборку можно сохранить), пагинация 50/100/200;
   - показ/скрытие колонок;
   - комментарий редактируется прямо в строке;
   - чекбоксы (включая «выбрать всё по фильтру») → массовые действия: отправить ссылку, включить, выключить, продлить, изменить комментарий, удалить.
3. **Создание**: один пользователь или пакет (количество либо список «имя; telegram id; комментарий»), срок (по умолчанию из настроек). Профили создаются только здесь, по заявкам и импортом — заранее ничего не создаётся. После нажатия «Создать» страница ждёт завершения apply и показывает уже рабочие ссылки.
3a. **Импорт** существующих профилей прокси — экран предпросмотра из раздела 3.10.
4. **Карточка пользователя**:
   - имя, **комментарий** (многострочное поле для своих заметок, сохраняется без рестартов), Telegram ID и username (редактируются), статус, создан, срок действия, отметка «импортирован» и исходное имя профиля;
   - дата первого соединения, последняя активность, признак «онлайн»;
   - ссылка `https://t.me/webproxy?server=…&secret=…` и `tg://webproxy?…` (копирование), QR-код (SVG, генерируется на сервере библиотекой `segno`);
   - **трафик**: график вверх/вниз + двухрычажный ползунок диапазона под графиком (ECharts `dataZoom`, файл библиотеки лежит в репозитории) + пресеты 24 ч / 7 дней / 30 дней / всё время; итоги «вверх / вниз / всего» пересчитываются для выбранного окна; детализация выбирается автоматически (минуты → часы → дни);
   - действия: отправить ссылку в Telegram, включить/выключить, продлить/сменить/снять срок, перевыпустить секрет, удалить (с подтверждением вводом имени);
   - журнал событий по пользователю.
5. **Заявки**: ожидающие запросы из бота, одобрить (с выбором срока) / отклонить.
6. **Рассылка**: выбор получателей, шаблон сообщения, предпросмотр, отчёт о доставке.
7. **Настройки**: срок по умолчанию (1 день / 1 месяц / 1 год / конкретная дата), режим выдачи (по одобрению / всем сразу), админы бота, токен бота, шаблоны сообщений, интервал опроса, сроки хранения статистики, глобальные лимиты relay, carrier_mode по умолчанию, хранение бэкапов, часовой пояс, смена пароля панели.
8. **Бэкапы**: список, создать, скачать, восстановить (восстановление = тот же apply-конвейер с откатом).
9. **Журнал**: аудит действий и история apply.

## 6. Telegram-бот

### 6.1 Пользователь

- `/start`: есть активный профиль → статус, срок, кнопка «Моя ссылка» (текст + QR-картинка). Нет профиля → кнопка «Запросить доступ».
- Режим **«всем без одобрения»**: профиль создаётся и применяется сразу; бот пишет «готовим…» и через несколько секунд, после успешного apply, присылает уже рабочую ссылку. То же при одобрении заявки админом.
- Режим **«по одобрению»**: заявка уходит админам с кнопками «Одобрить» (выбор срока) / «Отклонить»; пользователю — уведомление о решении.
- Защита: одна активная заявка на Telegram ID, ограничение частоты, чёрный список.
- Напоминание об истечении срока (по умолчанию за 3 дня; для срока в 1 день — выключено) и сообщение об истечении.

### 6.2 Админ (Telegram ID из списка админов)

- Список пользователей с пагинацией, поиском, фильтром по статусу и выбором сортировки (имя, последняя активность, трафик, срок).
- В карточке — просмотр и изменение комментария.
- Карточка: те же поля, что в панели; трафик за 24 ч / 7 дней / 30 дней текстом; QR.
- Включить / выключить, продлить, удалить (с подтверждением), отправить ссылку.
- Создать пользователя: диалог «имя → Telegram ID (можно пропустить) → срок → комментарий (можно пропустить)»; по завершении apply бот показывает рабочую ссылку.
- Заявки, переключение режима выдачи, статус apply, «бэкап сейчас», рассылка выбранным/всем.

### 6.3 Рассылка

- Сообщение по шаблону со ссылкой пользователя; inline-кнопка с `https://t.me/webproxy?...`, ссылка `tg://webproxy?...` текстом **[ПРОВЕРИТЬ НА СЕРВЕРЕ: какой формат реально открывается в клиенте]**.
- Темп ≤ 20 сообщений/с, обработка `RetryAfter`; ошибка 403 → `can_message = false`.
- Бот не может написать тому, кто не нажимал `/start`: у пользователей, созданных вручную по Telegram ID, показывать признак «бот не запущен» и исключать их из рассылки с пояснением в отчёте.

## 7. Сроки действия

- Настройка по умолчанию: 1 день / 1 месяц / 1 год / конкретная дата. Для пользователя срок можно переопределить при создании и в карточке.
- Планировщик раз в минуту: истёкшие → `status = expired`, профиль убирается из relay (секрет в MTProxy остаётся). Все истёкшие за минуту уходят одним apply, сразу.
- Продление возвращает `active` и сразу запускает apply.
- У импортированных пользователей срок не задан, пока владелец не поставит его вручную (по одному или массово из списка).

## 8. Инсталлятор и CLI

### 8.1 Запуск

```bash
curl -fsSL https://raw.githubusercontent.com/barakov-dot/tg-proxy-2/main/install.sh | bash -s -- \
  --panel-domain panel.example.com --bot-token <token> --admin-id <telegram id>
```

Без аргументов — интерактивные вопросы (чтение с `/dev/tty`). Необязательные: `--panel-login`, `--panel-password`, `--ref <тег/коммит>`. Предполагается, что репозиторий публичный; для приватного — вариант `git clone` с токеном, описать в README.

### 8.2 Шаги

1. Root, x86_64, Ubuntu 24.04 или Debian 13 (другие версии — отказ с пояснением).
2. **Проверка, что WEB proxy установлен** — до любых изменений на сервере: существуют `/usr/local/bin/tproxy-server`, `/etc/tproxy-server/config.json`, `/etc/tproxy-server/profiles.json`, `/opt/MTProxy/objs/bin/mtproto-proxy`, `/usr/local/bin/caddy`, `/etc/caddy/Caddyfile`; юниты `tproxy-server`, `mtproxy`, `caddy` активны; `curl http://127.0.0.1:8081/healthz` отвечает. Если нет — вывести, какие именно проверки не прошли, ссылку на README апстрима и **остановиться с кодом 1, ничего не меняя**.
3. Проверки: домен панели ≠ hostname прокси; DNS домена панели указывает на этот сервер (иначе Caddy не получит сертификат — предупредить и спросить); порты 2400–2463, 8900–8963, 8090 свободны; nftables поддерживает счётчики на элементах наборов; sha256 бинарника relay — в списке проверенных (иначе предупреждение).
4. `apt-get install` python3-venv, git, sqlite3, nftables; клон в `/opt/tgpanel`; venv; `pip install --require-hashes -r requirements.lock`.
5. Каталоги: `/etc/tgpanel` (`0700`), `/var/lib/tgpanel`, `/var/backups/tgpanel`.
6. **Начальный бэкап** исходного состояния (`pre-install`, не ротируется).
7. Генерация случайного пути, логина и пароля (если не заданы); токен бота и секреты приложения — в `/etc/tgpanel/tgpanel.env` (`0600`).
8. Таблица nft, юниты. Напоминание остановить прежнего бота и ожидание подтверждения. Показ найденных в `profiles.json` профилей и предложение импортировать их сейчас (раздел 3.10: предпросмотр, распознанные Telegram ID, предупреждение остановить прежнего бота). При отказе существующие профили остаются в `profiles.json` нетронутыми и продолжают работать вне панели, импорт доступен позже.
9. Блок панели в Caddyfile → validate → restart caddy → ожидание и проверка сертификата Let's Encrypt для домена панели (раздел 3.8; существующий действительный сертификат используется повторно).
10. Первый apply → запуск `tgpanel.service` → самопроверка.
11. Итог на экран один раз: URL панели, логин, пароль, имя бота, путь к бэкапу.

Повторный запуск = обновление (идемпотентно, данные и доступы сохраняются).

### 8.3 CLI `tgpanel`

`status`, `doctor` (все проверки из 8.2 и раздела 3), `apply`, `import [--dry-run] [--csv файл] [--id-regex выражение]`, `legacy-mtproxy on|off`, `backup`, `restore <файл>`, `show-url`, `reset-password`, `repair` (вернуть блок Caddy, nft, юниты), `update [--ref]`, `uninstall` (восстановить `pre-install`, убрать юниты, пулы, таблицу nft; данные — по флагу `--purge`).

## 10. Тесты и CI

- **Unit**: аллокатор (`secrets_per_process` = 16 и 15, заполнение, освобождение слотов, новый пул), выдача адресов, рендер всех файлов (сверка с фикстурами), правка `config.json` с сохранением неизвестных ключей, расчёт лимитов, сроки, дельты счётчиков и сбросы, порог активности.
- **Конвейер** на `FakeSystemOps`: успех, сбой на каждом шаге → откат; одна операция = один apply (в том числе пакетная); параллельные операции выполняются по очереди; ссылка не выдаётся до успешного apply.
- **Импорт**: сохранение секретов (включая `dd`), извлечение Telegram ID из имён `user_<id>`, сверка с `mtproxy.secrets`, CSV, дубли, повторный запуск без изменений, раскладка по пулам по 16, неуправляемые профили при отказе от импорта не теряются, обнаружение постороннего изменения `profiles.json`.
- **Web**: вход, CSRF, ограничение попыток, CRUD, массовые действия; сортировка по каждой колонке и каждый фильтр списка (белый список полей — имя колонки из запроса не подставляется в SQL). **Bot**: сценарии через тестовый диспетчер aiogram.
- **Shell**: `shellcheck` для `install.sh` и скриптов; тест ветки «прокси не установлен» в контейнерах `ubuntu:24.04` и `debian:13` (должен выйти с кодом 1 без изменений).
- **CI** (GitHub Actions): ruff, mypy, pytest, shellcheck — на каждый push.
- **На сервере**: `scripts/server-selfcheck.sh` и чек-лист из фазы 8.

## 12. Правила безопасности и запреты

- Сервис работает от root → внешние команды только списком аргументов (без shell), все значения в них — из БД после валидации; имена профилей только `u<id>`.
- Панель слушает только `127.0.0.1`. Порты пулов и статистики закрыты извне правилом nft; README напоминает про firewall провайдера.
- Секреты пользователей, токен бота, bridge-URL не попадают в логи, аудит, сообщения об ошибках, URL и коммиты. Бэкапы и файлы с секретами — `0600`, каталоги — `0700`.
- Не включать access-логи Caddy. Не менять блок прокси в Caddyfile, юниты и файлы апстрима, кроме: `profiles.json`, раздела `limits` в `config.json`, добавления своего блока в Caddyfile.
- Любая запись в файлы прокси — только через apply-конвейер с бэкапом и откатом. Никаких «быстрых правок» в обход.
- Не вызывать `/readyz` в цикле (ложная активность по всем пользователям).
- Зависимости закреплены с хешами; статика фронтенда лежит в репозитории.

## 13. Решения по умолчанию (владелец может поправить до старта)

1. Язык интерфейса панели и бота — русский; тексты вынесены в один модуль.
2. Истечение срока = выключение, а не удаление; данные и статистика сохраняются.
3. Полное удаление стирает и статистику пользователя (в бэкапе она остаётся).
4. Формат секрета для новых пользователей — обычные 32 hex без префикса `dd`; у импортированных секрет сохраняется как был.
5. `carrier_mode` по умолчанию `https` (самый совместимый); меняется глобально и на пользователя.
6. Варианта «бессрочно» в сроке по умолчанию нет (только 1 день / месяц / год / дата); для отдельного пользователя срок можно снять вручную. Импортированные — без срока.
7. Push идёт прямо в `main` после каждой задачи с зелёными тестами.
8. Второй фактор (TOTP) для панели — не в первой версии.
9. Telegram ID при импорте берётся из имени профиля `user_<id>`; прежнего бота владелец останавливает сам; старый процесс MTProxy на 2398 после импорта остаётся запущенным вхолостую, отключается командой по желанию.
10. Предел секретов на процесс — 16 по документации, настройка; снижается до 15, если проверка на сервере покажет, что 16-й ломает процесс.
